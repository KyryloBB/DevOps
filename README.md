## Опис застосунку

Веб-застосунок призначений для створення та відстеження задач (Task Tracker). Кожна задача має назву, статус (pending/done) та дату створення. Застосунок реалізований на Node.js з використанням Fastify і PostgreSQL.

## Технологічний стек

- Node.js + JavaScript
- Fastify (веб-фреймворк)
- PostgreSQL (база даних)
- npm (менеджер пакетів)

## Налаштування середовища для розробки та запуску

### Передумови

1. **Node.js** (рекомендовано v18 або вище) — [офіційний сайт](https://nodejs.org/)
2. **PostgreSQL** (локально або віддалений сервер) — [офіційний сайт](https://www.postgresql.org/)

## Запуск

1. Клонувати репозиторій `git clone https://github.com/KyryloBB/DevOps.git` 
2. Встановити залежності `npm install`
3. Налаштувати `config.json` для підключення до локальної БД (приклад нижче)
4. Запустити міграції БД `npm run migrate` (скрипт можна запускати повторно без ризику)
5. Запустити веб-застосунок `node server.js`

### Приклад `config.json`

```json
{
  "server": {
    "host": "127.0.0.1",
    "port": 5200
  },
  "database": {
    "host": "localhost",
    "port": 5432,
    "user": "postgres",
    "password": "your_password",
    "database": "task_tracker"
  }
}
```

## Документація API-ендпоінтів

* `GET /` - (text/html) відображає список усіх ендпоінтів бізнес-логіки застосунку.
* `GET /health/alive` - Перевіряє працездатність сервісу (завжди повертає 200).
* `GET /health/ready` - Перевіряє підключення сервісу до бази даних. У разі помилки підключення повертає HTTP 500 з коротким описом.
* `GET /tasks` - Виводить список усіх завдань з пoлями: `id, title, status, created_at`. *Залежно від заголовку `Accept`API автоматично повертає HTML-сторінку або чистий JSON.* Також виводить кнопки для створення задач та оновлення статусу вже існуючих задач на done.
* `POST /tasks`- Створює нове завдання зі статусом pending. Приймає параметр `title`.
* `POST /tasks/:id/done` - Змінює статус задачі з вказаним id на done.

## Тестування веб-сервісу

1. **Перевірка запуска веб-сервісу:** Відкрив браузер за адресою `http://127.0.0.1:5200/` та побачив головну сторінку з переліком усіх ендпоінтів бізнес-логіки застосунку.
2. **Перевірка обробки ендпоінтів** У браузері перевірив коректність обробки всіх ендпоінтів з типом `GET`. Для перевірки обробки ендпоінтів з типом `POST` використав утиліту Postman.

**Примітка:** На цьому етапі роботи перевірка взаємодії з БД неможлива, оскільки вона не розгорнута на робочій машині. Ця взаємодія стане доступною в *Лабораторній роботі 2* після розгортання PostgreSQL у Docker Compose.\
Ознакою коректної обробки `POST` ендпоінтів є наступний response:

```json
{
    "statusCode": 500,
    "code": "ECONNREFUSED",
    "error": "Internal Server Error",
    "message": ""
}
``` 

# Лабораторна робота 2 (Контейнеризація)

Була проведена контейнеризація застосунку. Тепер його можно не налаштовувати вручну та запускати за допомогою Docker. Також до застосунку був доданий сервіс nginx , який працює як revers-proxy і 
маршрутизує трафік до контейнера веб.

**Контейнери:** task_tracker_db, task_tracker_web, task_tracker_nginx

## Технологічний стек

- Node.js + JavaScript
- Fastify (веб-фреймворк)
- PostgreSQL (база даних)
- npm (менеджер пакетів)
- nginx (reverse-proxy)
- Docker / Docker Compose

## Інструкція з запуска застосунка:

1. Клонувати репозиторій
2. Налаштувати `config.json` для підключення до локальної БД (приклад нижче)
3. Зібрати та запустити всі сервіси у фоновому режимі `docker compose up -d --build`
3. Відкрити браузер за адресою `http://127.0.0.1:80/`

### Приклад `config.json`

```json
{
  "server": {
    "host": "0.0.0.0",
    "port": 5200
  },
  "database": {
    "host": "db",
    "port": 5432,
    "user": "postgres",
    "password": "your_password",
    "database": "task_tracker"
  }
}
```

## Тестування веб-сервісу

1. **Перевірка запуска веб-сервісу:** Відкрив браузер за адресою `http://127.0.0.1:80/` та побачив головну сторінку з переліком усіх ендпоінтів бізнес-логіки застосунку.
2. **Перевірка наявності списка завдань:** Відкрив браузер за адресою `http://127.0.0.1:80/tasks` та побачив сторінку з переліком існуючих завдань, полем для створення нових задач, а також кнопку для позначенння завдання, як виконаного.
3. **Створення нового завдання:** Увів в поле назву нового завдання та натиснув на кнопку "Створити завдання", після чого завдання відобразилося в таблиці нижче.
4. **Позначення існуючого завдання як виконаного:** Натиснув на кнопку "Виконане" поруч з новим завданням, після чого статус завдання змінився з "pending" на "done".
5. **Ізоляція ендпоінтів:** Спробував отримати доступ до службових ендпоінтів `/health/alive` та `health/ready` , проте nginx заблокував мої запити із поверненням HTTP-коду `403 Forbidden`.

### Особливості контейнеризації
* Сервіси піднімають в окремо створенній мережі `mywebapp_net`
* Дані БД зберігаються у volume `pg_data` , що дає їм змогу пережити перезапуск контейнерів чи системи. 

# Лабораторна робота 4 (IaC)

## Відомості про архітектурну систему

Система розгорнута на двох віртуальних машинах (Ubuntu 24.04) у межах однієї мережі:

* **VM1 (worker-node):**
  * Містить Nginx (Reverse Proxy) та веб-застосунок.
  * Nginx слухає порт `80` на всіх інтерфейсах VM, клієнти з'єднуться за IP-адресою worker `192.168.122.10`.
* **VM2 (db-node):** 
  * Містить базу даних PostgreSQL.
  * Прямий доступ ззовні заблокований. База даних приймає підключення виключно з IP-адреси `worker-node`.

### Користувачі в системі

* `ansible` - Користувач для автоматичного налаштування (створений через cloud-init). Присутній на обох VM.
* `teacher` - Користувач для перевірки роботи. 
Присутній на обох VM.
* `app` - Системний користувач, від якого запускається 
застосунок. Присутній тільки на VM із застосунком. 
* `operator` - Користувач для керування веб-застосунком та nginx. Присутній тільки на VM із застосунком. 

## Підготовчий етап
Для створення віртуальних машин за допомогою інструменту [Terraform](https://developer.hashicorp.com/terraform) використовується провайдер [libvirt](https://registry.terraform.io/providers/dmacvicar/libvirt/latest/docs) , тому перед використанням Terraform треба підготувати середовище.
1. Встановити пакети KVM та libvirt
```shell
sudo apt update
sudo apt install -y qemu-kvm libvirt-daemon-system libvirt-clients 
```
2. Додати вашого користувача в групи libvirt та kvm, щоб запускати Terraform без sudo
```shell
sudo usermod -aG libvirt,kvm $USER
newgrp libvirt 
```
3. Увімкнути та запустити стандартну мережу default
```shell
sudo virsh net-autostart default
sudo virsh net-start default
```
4. Згенерувати пару ssh ключів
```shell
ssh-keygen -t ed25519
```
5. Скопіювати публічний ключ в директорію .ssh в теці проєкту
```shell
cp ~/.ssh/ed25519.pub '<your_path>'/.ssh/ansible_key.pub
```

## Інструкція з розгортання інфракструктури

### Provisioning (Terraform) 

Створення віртуальних машин
1. Перейти в директорію [terraform](terraform/)
2. Ініціалізувати провайдера
```shell
terraform init
```
3. Запустити створення інфраструктури
```shell
terraform apply -auto-approve
```

### Configuration Management (Ansible)

[Ansible](https://docs.ansible.com/) налаштовує сервери (встановлення nginx, PostgreSQL, створення користувачів, розгортання коду) на віртуальних машинах, які були створені на попередньому етапі. Налаштування виконується **ідемпотентно**.

1. Встановити колекцію модулів для роботи Ansible з PostgreSQL
```shell
ansible-galaxy collection install community.postgresql
```
2. Перейти в директорію [ansible](ansible/)
3. Запустити налаштування
```shell
ansible-playbook -i inventory.ini site.yml
```

## Перевірка працездатності

Після успішного виконання Ansible-плейбука застосунок повністю готовий до роботи. Клієнти взаємодіють із системою через Reverse-Proxy (Nginx).

Для перевірки роботи застосунку виконайте HTTP запит до вузла worker.

**Перевірка роботи веб-застосунку:**\
`curl http://192.168.122.10/health/alive`

**Перевірка успішного з'єднання веб-застосунку з БД:**\
`curl http://192.168.122.10/health/ready`
